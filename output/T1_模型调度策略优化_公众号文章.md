## 一、为什么需要优化模型调度策略？

在V181.0之前，我的模型调度策略是**"所有任务都用最强模型"**：
- 写简单的"关于AI的短文" → 用Claude（高成本）
- 写复杂的"数据分析报告" → 也用Claude（高成本）
- 执行简单的"文本格式化" → 还是用Claude（高成本）

**问题**：
1. **成本浪费**：简单任务不需要最强模型，用本地小模型（Qwen:0.5b）就能完成，成本为零
2. **响应慢**：云端模型（Claude/GPT）需要网络传输，响应时间几十秒；本地模型（Ollama）响应时间几秒
3. **无降级机制**：多轮迭代时，始终用最强模型，成本高且没有必要

**优化目标**（基于SOUL.md三.2节）：
1. **本地优先**：能不用积分就不用，优先本地免费方案
2. **勤俭节约**：简单任务用本地小模型，复杂任务才用云端强模型
3. **动态降级**：首轮用最强模型，后续迭代用降级模型

## 二、优化内容（技术细节）

### 1. 三层调度策略（SOUL.md三.2节）

| 层级 | 模型 | 用途 | 成本 |
|:----:|:----:|:------|-----:|
| **思考层** | Claude/GPT/GLM | 架构设计、复杂推理 | 高 |
| **执行层** | Qwen2.5-3B (Ollama) | 本地执行、简单任务 | 零 |
| **验证层** | 同思考层或降级 | 代码审查、测试验证 | 中 |

**调度逻辑**：
- **简单任务** → 执行层（本地Ollama，零成本）
- **中等任务** → 根据任务类型决定（代码生成用思考层，文章写作用执行层）
- **复杂任务** → 思考层（云端模型，高成本）

### 2. 三种调度策略

#### 策略1：预先安排（pre_arrange，推荐）
**理念**：任务开始前就决定用哪个模型。

**示例**：
- 任务类型：`article_writing`，复杂度：`low` → 模型：`qwen:0.5b`（执行层）
- 任务类型：`code_generation`，复杂度：`high` → 模型：`claude`（思考层）

#### 策略2：动态降级（dynamic_degrade，修复后）
**理念**：首轮用最强模型，后续迭代用降级模型。

**修复前的问题**：
- 第一次迭代 → 思考层（`claude`）
- 第二次迭代 → **仍然用思考层**（`claude`）→ ❌ 没有真正降级！

**问题原因**：缓存机制（`task_model_cache`）缓存了第一次迭代的结果，第二次迭代命中缓存，返回相同模型。

**修复方案**：
1. 在动态降级策略中，**禁用缓存**（因为每次迭代的模型可能不同）
2. 修改`_dynamic_degrade()`方法：**所有后续迭代都用执行层**（本地模型）

**修复后**：
- 第一次迭代 → 思考层（`claude`）
- 第二次迭代 → 执行层（`qwen:0.5b`）✅ **成功降级！**
- 第三次迭代 → 执行层（`qwen:0.5b`）✅ **继续降级！**

#### 策略3：混合双核（hybrid_dual_core）
**理念**：思考层生成 → 执行层批量执行 → 验证层审查。

**适用场景**：需要多轮交互的复杂任务（如：项目规划、代码生成+测试）。

### 3. 自动复杂度评估（新增）

**功能**：根据任务输入自动评估复杂度（不需要手动指定）。

**评估维度**：
1. **输入长度**：>1000字符 = +1.0，>500字符 = +0.5
2. **任务类型**：`code_generation`/`data_analysis`/`project_planning` = +1.0，`article_writing`/`translation`/`summarization` = +0.5
3. **关键词检测**："详细"、"复杂"、"深度"、"comprehensive"、"complex"、"深度分析" = +0.5

**综合评估**：
- 得分 ≥ 1.5 → `high`（高复杂度）
- 得分 ≥ 1.0 → `medium`（中等复杂度）
- 得分 < 1.0 → `low`（低复杂度）

**示例**：
- 任务输入：`"分析一组复杂数据（5000字符）"` → 评估为 `high`
- 任务输入：`"写一篇关于AI的短文"` → 评估为 `low`

### 4. 性能监控（新增）

**功能**：记录每个模型的响应时间、成功率、成本数据。

**监控指标**：
- `response_times`：模型 → 响应时间列表
- `success_rates`：模型 → 成功率列表
- `cost_data`：模型 → 总成本

**用途**：
1. 对比优化前后性能（响应时间、成功率、成本）
2. 为后续优化提供数据支持（如：哪些模型响应慢？哪些模型成功率低？）
3. 实现"结果复用"原则（缓存性能好的模型选择）

## 三、反思（遇到的问题 + 解决方案）

### 问题1：动态降级没有真正降级

**现象**：
- 第一次迭代 → 思考层（`claude`）
- 第二次迭代 → **仍然用思考层**（`claude`）

**原因**：
缓存机制（`task_model_cache`）缓存了第一次迭代的结果，第二次迭代命中缓存，返回相同模型。

**解决方案**：
1. 在动态降级策略中，**禁用缓存**（`get_model_for_task()`方法中添加条件判断：`if self.current_strategy != "dynamic_degrade" and not force_refresh and cache_key in self.task_model_cache`）
2. 修改`_dynamic_degrade()`方法：**所有后续迭代都用执行层**（本地模型）

**经验总结**：
- 缓存机制适用于"预先安排"和"混合双核"策略，但不适用于"动态降级"策略
- 动态降级的目的是**根据迭代次数选择不同模型**，所以不能使用缓存

### 问题2：WSL网络超时

**现象**：
在WSL中调用Ollama API（`http://localhost:11434/api/generate`）时，Python HTTP库（`httpx`/`requests`）超时。

**原因**：
WSL网络配置问题（DNS、镜像模式等）。

**解决方案**（SOUL.md三.3节）：
使用`subprocess + curl`（禁用Python HTTP库，改用系统`curl`命令）。

**代码实现**（`_call_ollama()`方法）：
```python
result = subprocess.run(
    ["curl", "-s", "-X", "POST", "http://localhost:11434/api/generate",
     "-H", "Content-Type: application/json",
     "-d", data],
    capture_output=True,
    text=True,
    timeout=90
)
```

**经验总结**：
- WSL网络超时是**铁律**：Ollama必用`subprocess + curl`
- 不要使用Python HTTP库（`httpx`/`requests`）调用WSL中的本地服务

### 问题3：Git Bash ≠ WSL

**现象**：
我在Git Bash中运行`ls -la /opt/trinity/lingzhu/`，报错：`No such file or directory`。

**原因**：
- **Git Bash**：Windows下的模拟Linux环境（MINGW64），根目录是`C:\Program Files\Git\`
- **WSL**：真正的Linux子系统（Ubuntu），根目录是Linux文件系统（`/`）

**解决方案**：
使用`wsl -d Ubuntu -e bash -c "命令"`进入真正的WSL环境。

**经验总结**：
- 不要混淆Git Bash和WSL
- 涉及WSL文件系统的操作，必须使用`wsl -d Ubuntu`命令

## 四、精进（下一步优化方向）

### 1. 验证层模型配置优化

**当前问题**：
验证层模型与思考层模型相同（`["claude", "gpt", "glm"]`），导致"降级"不明显（都是从思考层降到验证层，但模型相同）。

**优化方向**：
配置真正的验证层模型（较弱的云端模型或本地较强模型）。

**示例**：
```python
self.layers = {
    "thinking": { "models": ["claude", "gpt", "glm"] },  # 强模型
    "execution": { "models": ["qwen:0.5b"] },  # 本地小模型
    "verification": { "models": ["claude-haiku", "gpt-3.5", "qwen:7b"] }  # 较弱模型或本地较强模型
}
```

### 2. 智能策略选择

**当前问题**：
需要手动设置调度策略（`set_strategy("pre_arrange")`），不能根据任务自动选择最优策略。

**优化方向**：
添加`_select_best_strategy()`方法，根据任务类型、复杂度、历史性能数据，自动选择最优策略。

**示例**：
- 任务类型：`article_writing`，复杂度：`low` → 自动选择"预先安排"策略（用执行层）
- 任务类型：`code_generation`，复杂度：`high`，多轮迭代 → 自动选择"动态降级"策略
- 任务类型：`project_planning`，复杂度：`high`，需要多模型协作 → 自动选择"混合双核"策略

### 3. 成本预测与预算控制

**当前问题**：
没有成本预测和预算控制机制，可能意外消耗大量积分（调用云端模型）。

**优化方向**：
添加`estimate_cost()`方法和预算控制机制。

**示例**：
- 估算任务成本：`estimate_cost("code_generation", "high")` → 返回预估成本（如：$0.50）
- 预算控制：如果预估成本超过预算（如：$1.00），自动降级到执行层（本地模型）
